## Executive Summary

**Overall security verdict: No password or PIM leaks, no shell injection, and no unauthenticated takeover paths were introduced. The password path (`include/actions.php`) remains fundamentally sound.**

The most important security properties hold across all seven commits:
- Passwords and *PIMs* (VeraCrypt's Personal Iterations Multiplier) still travel strictly over *standard input* (a private channel between processes), never appearing in command lines, environment variables, files, logs, notifications, or HTTP responses. `vcm_run()`'s non-blocking write/read loop (`B6`) handles partial writes and broken pipes cleanly without leaking secrets.
- Every external program call in `vcmount check` (`docker ps`, `docker stop`, `docker inspect`, `blkid -p`, `notify`) uses fixed argument arrays with no shell interpolation and absolute system paths (`program()`), so running from cron as `root` with a minimal `$PATH` is safe from command or `PATH` injection.
- Rebuilding the Slackware package in memory at release commit `52e4b07` matches `plugin/veracrypt.mount.plg` (`2026.11.27o`, SHA-256 `4d0f409b64c5e5af7677ebdfa5002cd706687d5870c90a7c07fd211883b6bbf1`) byte-for-byte. No secrets or personal credentials appear in `b90530d..HEAD`.

**However, this audit found several real security/safety weaknesses and functional bugs in the new minute check (`vcmount check`), the `.plg` cron setup, and the follow-up fixes:**
1. **`stray_dependents()` (`DOC-6`, running every minute as `root`) has path-safety, stale-config, and runaway-retry flaws:** it reads `volumes.json` before `docker ps` and `take_lock()` and never reloads it under the lock; its `remove_empty_tree()` check does not guard against parent *symbolic links* (shortcuts pointing elsewhere) or custom `/mnt/addons/...` paths and deletes empty subdirectories even inside non-empty folders; and an unstoppable dependent triggers a lock-holding retry and a flash-archived warning notification **every minute forever** (**S1**).
2. **The `.plg` cron handling has a crontab-concatenation hazard, rewrites the USB flash drive on every boot, and can race with cron during removal:** the fallback `cat /etc/cron.d/root; cat veracrypt.mount.cron` lacks a guaranteed newline between files, `rm -f` + `<FILE>` deletes and rewrites `veracrypt.mount.cron` on `/boot` on every reboot, and removal runs `removepkg` before removing the cron job while misreporting a cron lock collision as "a volume is still mounted" (**S2**).
3. **Minor regressions in `include/actions.php` (`B6`):** `$stdin` (holding the plaintext password/PIM) is no longer cleared as soon as the pipe write finishes — it now stays in PHP-FPM memory for the full unlock wait (up to 180–300 seconds) — and `vcm_stop()`'s `SIGKILL` can orphan child processes like `docker stop` while releasing the lock (**S3**).
4. **High-impact functional bugs in the new idle lock (`LIFE-8`) and `DOC-6`:**
   - Naming a volume with digits only (e.g. `2026`, valid under `NAME_PATTERN`) **completely breaks the idle lock** due to PHP converting numeric JSON keys to integers (**B1**).
   - `idle_blockers()` fails to exclude **dependent** containers that bind-mount host paths 1:1 (such as `/mnt/addons/<name>` or `/mnt/user`), permanently blocking idle lock on those volumes (**B2**).
   - `stray_dependents()` treats `unlocked` (not mounted) volumes as mounted, and only cleans up/warns about the **first** volume of a multi-volume dependent (**B3**).
   - `stopOther()` in `js/vcmount.js` still has the stale-callback race that `B8` fixed in `otherBusy()` and `settle()` (**B4**).

## S1. Medium: `stray_dependents()` (`DOC-6`, cron as `root`) has parent-symlink and partial-deletion risks, uses stale config under the lock, and can flood flash notifications and lock out the plugin

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `remove_empty_tree()` (lines 2790–2805) and `stray_dependents()` (lines 2818–2880).
- **What could go wrong:**
  `vcmount check` runs every minute as `root` from cron. `stray_dependents()` has three safety/security gaps:
  1. **Parent symlinks and custom paths in `remove_empty_tree()`:**
     When a stray dependent is stopped, lines 2864–2866 check:
     ```php
     $point = $config[$volume]['mount_at'];
     if ($done && is_dir($point) && !is_link($point) && !in_array($point, mount_points(), true)) {
         if (strncmp($point, '/mnt/addons/', 12) === 0 && remove_empty_tree($point)) {
     ```
     - Because `check_config()` allows any plain path under `/mnt/` as `mount_at` (for example `/mnt/addons/sub/vault` or `/mnt/addons/other-plugin`), `strncmp($point, '/mnt/addons/', 12) === 0` matches *any* folder under `/mnt/addons/`, not only this plugin's own `/mnt/addons/<volume>`.
     - Unlike `check_mount_point()` (which walks every parent component for symlinks after audit `S1`), line 2865 only checks `!is_link($point)` on the final component. If an ancestor component (e.g. `/mnt/addons/sub`) is a symlink pointing elsewhere, `root` follows it and calls `remove_empty_tree()` outside `/mnt/addons/`. (Because `remove_empty_tree()` only calls `rmdir()`, it cannot delete files, only empty directory trees.)
     - Furthermore, `remove_empty_tree()` deletes empty subdirectories *while* recursing before checking sibling entries: if Docker wrote `/mnt/addons/vault/sub1` (empty) and `/mnt/addons/vault/sub2/data.db` (non-empty), `remove_empty_tree()` deletes `sub1` before returning `false`.
  2. **Time-of-check to time-of-use (*TOCTOU*) stale configuration across `docker ps`:**
     A *TOCTOU race* happens when state changes between checking it and acting on it. Line 2820 calls `$config = load_config()` *before* running `docker ps` (up to 10 seconds) and *before* calling `take_lock()` on line 2848. Under the lock (line 2849), `stray_dependents()` refreshes `$live = live_volumes()`, **but never reloads `$config` or recomputes `$allowed`/`$wanted`**. If the user saves a config edit (removing a container from dependents, or attaching it to an already-mounted volume) while `docker ps` is running, cron stops a container that is no longer a stray dependent or cleans up a stale `$point`.
  3. **Runaway lock-holding and flash-write flood on an unstoppable dependent (availability / flash wear):**
     If `docker stop` fails or the container remains running (`$done === false`), `stray_dependents()` has **no backoff or deduplication** (unlike `command_idle_check()`, which sets `warned = true` and resets the timer). Every single minute, cron acquires `/var/run/vcmount.lock`, blocks for up to `grace + 30` seconds (up to **630 seconds** per container!), and calls `log_event($message, true)` — writing a warning notification to `/boot/config/plugins/dynamix/notifications/archive/` on the USB flash drive up to 1,440 times per day while permanently locking out web UI mounts/dismounts and array-stop hooks (`code 6`).
- **How likely:** Low for parent symlinks under `/mnt/addons/`; Low-Medium for a stuck container or config edit racing with cron.
- **How bad:** Medium — unintended empty-directory removal, stopping a freshly detached container, or persistent engine lockout and flash-drive notification flooding if a container fails to stop.
- **Suggested fix:**
  1. Reload `$config = load_config()` and recompute `$allowed`/`$wanted` *after* `take_lock()` succeeds.
  2. Only run `remove_empty_tree($point)` when `$point === "/mnt/addons/$volume"` and `!is_link('/mnt/addons')` (exact match to this plugin's own mount point, never arbitrary nested paths under `/mnt/addons/`).
  3. Split `remove_empty_tree()` into a read-only check (`tree_is_empty($dir)`) followed by deletion only if the entire tree contains no files or symlinks.
  4. Track failed `stray_dependents()` stop attempts in a RAM state file (or backoff map): notify once per container and back off (e.g. 15–60 minutes) instead of retrying and writing flash notifications every minute. Also consider honoring `array_started()` inside the loop before stopping additional containers so cron does not fight an array stop.

## S2. Medium-Low: `.plg` cron setup concatenates without a newline, rewrites `/boot` on every boot, and races with cron on removal

- **Confidence:** Confirmed by reading `plugin/veracrypt.mount.plg`. Exact `update_cron` / `crontab -c /etc/cron.d` behavior on Unraid 7.4 **needs verification on the server**.
- **Where:**
  - `plugin/veracrypt.mount.plg` (lines 48–74 and 98–119).
- **What could go wrong:**
  1. **Unsafe crontab concatenation when `/etc/cron.d/root` lacks a trailing newline (line 71):**
     ```bash
     if ! grep -qF 'vcmount check' /etc/cron.d/root 2>/dev/null; then
       { cat /etc/cron.d/root 2>/dev/null; cat &flash;/&name;.cron; } | crontab -c /etc/cron.d -
     fi
     ```
     If `/etc/cron.d/root` exists without a trailing newline (for example from another plugin's `.cron` file), concatenating the two files directly glues `# VeraCrypt Mount: ...` onto the end of the previous cron job's command line, corrupting that root cron job.
     Additionally, if an older `vcmount idle-check` line is still in `/etc/cron.d/root` when this fallback runs, both lines end up in the root crontab (and `grep -qF` matches comments as well as active lines).
  2. **Unnecessary USB flash delete-and-rewrite on every reboot (lines 48–61):**
     Unraid runs every install `<FILE>` section of every `.plg` file on **every boot** (not only on plugin updates). Line 52 unconditionally runs `rm -f &flash;/&name;.cron` and line 56 immediately writes the identical file back to `/boot/config/plugins/veracrypt.mount/veracrypt.mount.cron` — wearing the USB flash drive on every reboot even when nothing changed.
  3. **Removal races with cron and leaves runtime files behind (lines 98–111):**
     - Line 101 runs `vcmount dismount --all`. If cron's `vcmount check` happens to hold `/var/run/vcmount.lock` at that instant, `dismount --all` exits with **code 6** (busy), and line 102 aborts removal with the misleading message `"Not removed: a volume is still mounted and in use"` even when zero volumes are mounted.
     - Line 106 runs `removepkg &name;` *before* line 109–110 deletes `&flash;/&name;.cron` and runs `update_cron`, leaving a brief window where cron still references the deleted script.
     - Line 111 deletes `/var/run/vcmount.idle` and `/var/run/vcmount.idle-error`, but leaves `/var/run/vcmount.lock`, `/var/run/vcmount.cancel`, and `/var/run/vcmount.unlocking` behind.
- **How likely:** Certain for the boot-time flash rewrite; Low for missing-newline corruption or removal/cron collision.
- **How bad:** Low-Medium — broken adjacent root cron job if a newline is missing; unnecessary flash writes on every reboot; confusing removal failure if cron ran in the same second.
- **Suggested fix:**
  1. Before `<FILE Name="&flash;/&name;.cron">`, only delete the existing file if its content differs from the desired command:
     `grep -qF 'scripts/vcmount check ' &flash;/&name;.cron 2>/dev/null || rm -f &flash;/&name;.cron`
     (so normal reboots never touch `/boot`).
  2. In line 71, insert a blank line between the files (`{ cat /etc/cron.d/root 2>/dev/null; echo ""; cat &flash;/&name;.cron; }`) and strip any stale `vcmount idle-check` line if present.
  3. In `Method="remove"`, distinguish code 6 (retry briefly or tell the user another action is running) from code 5 (volume in use), remove `&flash;/&name;.cron` and call `update_cron` right after dismount succeeds (before `removepkg`), and remove all `/var/run/vcmount.*` files.

## S3. Low: Password/PIM `$stdin` stays in PHP-FPM memory for the full unlock wait (B6 regression), and `vcm_stop()` can orphan engine child processes

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/include/actions.php`: `vcm_handle()` (lines 93–105, 140–150), `vcm_stop()` (lines 212–223), `vcm_run()` (lines 255–310).
- **What could go wrong:**
  1. **Longer secret lifetime in PHP memory:**
     Before `B6`, `vcm_run()` wrote `$stdin` to `$pipes[0]`, closed the pipe, and **immediately called `unset($stdin)`** before waiting for `vcmount` / `cryptsetup`. In the new combined read/write loop (lines 290–308), when the write completes on lines 296–299, `$input` is closed and set to `null`, **but `$stdin` is not cleared until line 308 (after `vcmount` exits) or line 273 (on timeout)**. For a slow unlock (large PIM or wrong password), the plaintext password and PIM now remain live in PHP-FPM memory for up to 180–300 seconds instead of milliseconds. (PHP's `unset()` does not overwrite RAM bytes, but releasing the variable immediately avoids keeping a live reference across a multi-minute wait.)
  2. **`vcm_stop()` `SIGKILL` leaves child processes running without the engine lock:**
     When `vcm_run()` hits `VCM_TIMEOUT` (300s), `vcm_stop()` sends `SIGTERM` to the PHP `vcmount` process and `SIGKILL` after 5 seconds.
     - For an active `cryptsetup` unlock, `vcmount` catches `SIGTERM`, kills `cryptsetup` within ~0.5s, and calls `lock_again()` — so normal unlocks clean up properly.
     - However, for `dismount --all` (where `command_dismount()` calls `watch_time()`, so `SIGTERM` only sets `$GLOBALS['vcm_stop'] = true` to finish the current volume) or any non-cancellable child (`docker stop`, `docker start`, `umount`, `mount`, `blkid`), `vcmount` stays alive past the 5-second grace period and `vcm_stop()` kills **only** `vcmount` with `SIGKILL`. Its child process (e.g. `docker stop -t 300`) stays orphaned in the background, while `/var/run/vcmount.lock` is immediately released (because `take_lock()` opens it with `'ce'` / `O_CLOEXEC`), allowing a second `vcmount` action to overlap with the orphaned child.
  3. **Minor check ordering on plain HTTP (`vcm_handle()`, lines 93–105 vs 140–142):**
     When `require_https` is on and a crafted `POST action=mount` arrives over plain HTTP, `vcm_handle()` runs `vcmount status <name> --json` and returns PIM/keyfile refusal messages before `vcmount mount --over-http` refuses plain HTTP. (Not a secret leak — an authenticated user already has `status`/`list` — just inconsistent refusal precedence.)
- **How likely:** Always for the extended `$stdin` lifetime; Low for `VCM_TIMEOUT` `SIGKILL` (only if an operation exceeds 300 seconds).
- **How bad:** Low — defense-in-depth secret exposure window in PHP-FPM memory; potential overlapping container stop after a 5-minute timeout.
- **Suggested fix:**
  1. Set `$stdin = null;` immediately inside `if ($wrote === false || $sent >= $length)` on line 298 (once written to the pipe, `$stdin` is never read again).
  2. Document the `SIGKILL` orphan edge case on 300s web timeouts (or pass `--within` on `dismount --all` from `actions.php` so `vcmount` finishes cleanly inside `VCM_TIMEOUT`).

## S4. Low (Defense-in-Depth / Privacy): `/var/run/vcmount.idle` is world-readable (`0644`) with volume names, and `write_marker()` is non-atomic

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `write_marker()` (lines 2548–2558), `idle_state()` (lines 2571–2584), `command_idle_check()` (line 2739).
- **What could go wrong:**
  1. **Saved volume names and activity timestamps stored world-readable (`0644`):**
     Unlike `/var/run/vcmount.unlocking` (which carefully stores only a timestamp and *"no name"*), `/var/run/vcmount.idle` stores every watched volume's exact saved name, device mapper node, I/O counts, and last-activity timestamp as JSON. Because `write_marker()` creates the file with the default umask (`0644`), any local non-root user or container given read access to `/var/run` can read saved volume names and usage times even when `"Show volume names in logs"` (`PRIV-1`) is off. (On standard Unraid, untrusted local users do not exist and containers do not mount `/var/run`, so this is defense-in-depth, extending earlier audit **S12**.)
  2. **Non-atomic rewrite causes torn reads during 5-second UI polling:**
     `write_marker()` runs `@unlink($path)`, then `fopen($path, 'x')`, then `fwrite()`. Because `vcmount list --json` (polled every 5 seconds without holding `LOCK_FILE`) calls `read_marker(IDLE_FILE)` concurrently, a poll landing between `unlink()` and `fclose()` sees a missing or half-written file, making `json_decode()` return `null` and causing the idle countdown to briefly flicker off in the Web UI.
- **How likely:** Very low for privacy exposure on standard Unraid; Low for brief UI flicker when cron and the 5-second poll collide.
- **How bad:** Low — metadata exposure to local non-root processes; brief visual flicker of idle status.
- **Suggested fix:** Move all runtime files (`lock`, `cancel`, `unlocking`, `idle`, `idle-error`) into `/var/run/vcmount/` created with mode `0700` (owned by `root`, verified not a symlink — closing earlier audit **S12** at the same time). Write `idle` to a temp file inside that directory with mode `0600` and atomically `rename()` it into place.

## B1. High (Confirmed): All-digit volume names (e.g. `2026`, `123`) completely break the idle lock (`LIFE-8`)

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `idle_state()` (line 2576).
- **What goes wrong:**
  `NAME_PATTERN` allows volume names consisting solely of digits (such as `2026` or `1`). When `command_idle_check()` saves `{"2026": {"dm": "dm-1", ...}}` to `/var/run/vcmount.idle` and `idle_state()` reads it back with `json_decode(..., true)`, PHP automatically coerces decimal-integer object keys from `string` to `int` (`2026`). Line 2576 then checks:
  ```php
  if (is_string($name) && preg_match(NAME_PATTERN, $name) && ...)
  ```
  Because `$name` is `int(2026)`, `is_string($name)` returns **`false`** and silently drops the entry on every single read! As a result:
  1. `command_idle_check()` treats the volume as newly mounted every minute, resets `since` to `time()`, and **never idle-locks the volume**.
  2. `idle_view()` always returns `locks_in => null`, so the countdown **never appears** in the Web UI.
- **How likely:** Low (depends on choosing an all-digit volume name), but 100% reproducible whenever triggered.
- **How bad:** High for that volume — the idle lock silently never fires.
- **Suggested fix:** Cast `$name = (string) $name;` at the top of the `foreach` loop in `idle_state()` before checking `preg_match(NAME_PATTERN, $name)` (matching lines 1632, 2096, 2699, 2829, and 3315).

## B2. High (Confirmed): `idle_blockers()` does not exclude dependent containers in `holders()`, permanently blocking idle lock when paths match 1:1

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `open_file_below()` (lines 2611–2621), `idle_blockers()` (lines 2630–2650), and `holders()` (lines 1777–1811).
- **What goes wrong:**
  1. **Dependent containers falsely flagged as blockers:**
     `idle_blockers()` runs two checks: `holders($point)` (lines 2633–2639) and `mount_users($device_number)['containers']` (lines 2643–2647). It filters out the volume's own dependent containers **only in the second loop**, relying on `holders()`'s comment that *"Programs inside a container are not seen here"*.
     That assumption breaks whenever a dependent container bind-mounts the host path at the **same path inside the container** (e.g. `-v /mnt/addons/vault:/mnt/addons/vault`, or `-v /mnt/user:/mnt/user` for `MNT-2` — both common on Unraid). In that case, `/proc/<pid>/fd/*` inside the container resolves to `$point/...`, so `holders($point)` returns the dependent container's process, `idle_blockers()` does **not** filter it out, logs `"still in use by ..."`, and **never** stops the dependent or idle-locks the volume.
  2. **Deleted open files missed by `open_file_below()`:**
     Line 2616 checks `if ($target !== false && below($target, $point) && is_file($target))`. If a Samba worker holds an open file that was unlinked/renamed, `readlink($fd)` ends with `" (deleted)"`, so `is_file($target)` returns `false` (and for symlinks inside the volume, `is_file($target)` follows them). Testing `is_file($fd)` directly on `/proc/$pid/fd/<n>` inspects the open descriptor itself even when unlinked.
  3. **`MNT-2` Samba directory handle stops dependents unnecessarily:**
     When a volume is mounted inside an Unraid user share (`MNT-2`, e.g. `/mnt/user/myshare/vault`) with no plugin share of its own, skipping `smbd` because only a directory is open causes `command_idle_check()` to call `do_dismount()`, which stops all dependent containers before `umount` fails with `EBUSY` (since `remove_share()` never closes the parent Unraid share `myshare`).
- **How likely:** Medium for users who configure dependents with matching mount paths or use `MNT-2` with idle lock.
- **How bad:** High for idle lock — the volume either never locks, or stops all its dependents and fails to dismount.
- **Suggested fix:**
  1. In `idle_blockers()`, extract any Docker container ID from `/proc/<pid>/cgroup` (`docker[-/]([0-9a-f]{64})`) for processes returned by `holders($point)` and skip them if they belong to one of `$volume['dependents']` (or skip all container PIDs in the `holders()` loop since `mount_users()` already checks all containers cleanly).
  2. In `open_file_below()`, check `is_file($fd)` instead of `is_file($target)`.
  3. Only apply the `smbd` directory-only exception when `$volume['share'] !== null` and the mount is not inside `/mnt/user/` (so `remove_share()` will actually disconnect `smbd`).

## B3. Medium-High (Confirmed): `stray_dependents()` (`DOC-6`) treats `unlocked` (not mounted) volumes as mounted and ignores 2nd..Nth volumes of a shared dependent

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `stray_dependents()` (lines 2826, 2853, 2859–2873).
- **What goes wrong:**
  1. **`unlocked` volumes are treated as mounted:**
     Lines 2826 and 2853 check `isset($live[$name])`. However, `live_volumes()` includes volumes whose `/dev/mapper/vcm-<name>` device exists even when `$live[$name]['mounted_at'] === null` (state `unlocked`, not mounted). If a volume is unlocked but unmounted, its mount folder is still empty RAM — yet `stray_dependents()` puts its dependents in `$allowed` and leaves them running and writing into RAM.
  2. **Only the first locked volume's mount folder is checked/cleaned:**
     If a container is a dependent of two locked volumes (`volA` and `volB`), line 2859 picks `$volume = $volumes[0]` (`volA`), and lines 2864–2873 only clean up or warn about `volA`'s mount folder. Any empty directory Docker created at `/mnt/addons/volB` — or worse, files the container wrote into `/mnt/addons/volB` in RAM — is left behind silently, causing the next mount of `volB` to fail without having warned the user.
- **How likely:** Low-Medium (multi-volume dependents or a volume stuck in `unlocked` state).
- **How bad:** Medium — dependent writes into RAM unstopped, or leaves stale files/folders on secondary volumes.
- **Suggested fix:** Replace `isset($live[$name])` with `($live[$name]['mounted_at'] ?? null) !== null` on lines 2826 and 2853, and iterate over *all* volumes in `$volumes` when removing empty folders and checking for stray files.

## B4. Medium (Confirmed): `stopOther()` still has the stale-callback race from B8, and `settle()` keeps `mounting = true`

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/js/vcmount.js`: `stopOther()` (lines 791–806) and `settle()` (lines 873–902).
- **What goes wrong:**
  1. **`stopOther()` lacks a `busyWatch` check:**
     Commit `85683de` fixed stale-callback races in `otherBusy()` and `settle()`, but missed `stopOther()`. Line 792 increments `busyWatch++`, yet never stores `var id = busyWatch;` or checks `if (id !== busyWatch) { return; }` inside its `.then()` and `poll()` callbacks.
     *Concrete scenario:* You click **"Stop that unlock"**, immediately click **Cancel** to close the dialog, and open the Mount dialog for another volume (and start unlocking it). Up to 5 seconds later, `stopOther()`'s polling finishes and calls `dialogError('The other unlock was stopped...')` — overwriting the new dialog's state, setting `mounting = false`, stopping the progress bar, and re-enabling the Mount button while your real unlock is still running.
  2. **Cancel during `settle()` cannot close the dialog:**
     When `act(data)` returns `a.lost` or `a.timed_out`, `submitMount()` calls `settle()` while `mounting` is still `true`. `settle()` can poll for up to 4 minutes (120 × 2s). If the server is unreachable or `a.timed_out` already stopped the engine, clicking Cancel invokes `cancelUnlock()` (which disables the Cancel button and writes an orphaned `/var/run/vcmount.cancel`) instead of letting the user close the dialog.
- **How likely:** Low-Medium (clicking Cancel right after "Stop that unlock", or after a dropped/timed-out request).
- **How bad:** Medium — corrupted mount dialog state or unclosable dialog during a connection drop.
- **Suggested fix:** Capture `var id = ++busyWatch;` in `stopOther()` and guard both `.then()` callbacks with `if (id !== busyWatch) { return; }`. In `settle()`, set `mounting = false` when `lost === 'timeout'` (or let Cancel abort `settle()` and close the dialog cleanly).

## B5. Medium (Confirmed): Idle-lock state bugs — stale countdown after remount, frozen `$now` across slow dismounts, and broken share after a failed idle dismount

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `idle_view()` (lines 2587–2595), `command_idle_check()` (lines 2697–2735).
- **What goes wrong:**
  1. **Stale `"locks soon"` / `"idle, held open"` after manual dismount and remount:**
     Neither `do_dismount()` nor `do_mount()` removes `$name` from `/var/run/vcmount.idle`, and `idle_view()` never compares `$entry['dm']` with the live device. If you manually dismount an idle (or `idle_blocked`) volume and remount it within the same minute, the Web UI falsely displays `"locks soon"` or `"idle, held open"` on the freshly mounted volume until the next cron run.
  2. **Frozen `$now` shortens idle timers of later volumes:**
     Line 2697 reads `$now = time()` once before the `foreach ($watched ...)` loop. If volume 1 is idle and `do_dismount()` takes 3 minutes stopping its dependents, volume 2 (newly mounted or active) gets `since => $now` (3 minutes in the past!), cutting a 5-minute idle lock down to 2 minutes.
  3. **Failed idle dismount leaves the share dead and dependents stopped:**
     If a file is opened in the window between `idle_blockers()` and `do_dismount()` (or `smbd` holds an `MNT-2` directory open), `do_dismount()` removes the SMB share and stops all dependents *before* `umount` fails with `CODE_BUSY`. `command_idle_check()` catches `Fail` and sets `since => $now, warned => true` — leaving the volume mounted with no SMB share and stopped dependents while showing `"idle, held open"`.
- **How likely:** Low-Medium (remounting within 60s, or multiple idle volumes with slow dependents).
- **How bad:** Medium — confusing stale UI state, premature lock of a second volume, or unexpectedly lost SMB share/dependents after a busy race.
- **Suggested fix:** Delete `$name` from `IDLE_FILE` inside `do_dismount()` and `do_mount()` on success; compute `time()` fresh inside the loop in `command_idle_check()`; and check `$entry['dm']` in `idle_view()`.
