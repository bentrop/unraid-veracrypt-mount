# Security Audit and Bug Review: VeraCrypt Mount for Unraid

- **Audit date:** 2026-11-27
- **Repository state reviewed:** commit `1d83816` (plugin version `2026.11.27a`, all 18 commits in git history)
- **Method:** Read-only review of every file under `src/`, `plugin/`, `scripts/`, `.github/workflows/`, `docs/`, `tests/`, and `mockups/`, plus the complete `git log -p` history and an in-memory check that the package checksum matches `plugin/veracrypt.mount.plg`. Nothing was modified, nothing was installed, and no server or external computer was contacted.
- **Scope:**
  - **Part 1 — Security Audit:** Secrets handling, web requests, command execution, files and paths, SMB sharing, system lifecycle hooks, Docker control, installation and release pipeline, privacy, repository history, and verification of all fixes from the three earlier reviews in `docs/REVIEW-secrets.md`.
  - **Part 2 — General Bug Review:** Logic errors, error handling, state and concurrency, Unraid-specific behaviour, input edge cases, web pages/JavaScript/accessibility, and code quality issues likely to cause future bugs.

---

## Executive Summary

**Overall security verdict: Fundamentally well designed, with no critical or high-severity secret leaks, and no unauthenticated takeover paths.**

The core architecture is solid:
- Passwords and *PIMs* (VeraCrypt's Personal Iterations Multiplier, a secret number that controls how hard it is to guess a password) travel only through *standard input* (the private data channel a program reads typed input from, invisible to other programs). They never appear in command lines, environment variables, files, logs, notifications, browser storage, or HTTP responses.
- Commands are started from fixed argument lists without a *shell* (a command interpreter such as Bash that can accidentally execute specially crafted text as commands).
- Web requests are protected by Unraid's login wall and *CSRF token* (a secret per-session code that proves a request genuinely came from Unraid's own web page, not from a malicious website open in another browser tab).
- The repository history contains **no** leaked passwords, keys, real PINs/PIMs, IP addresses, or personal e-mail addresses.
- Rebuilding the package in memory from `src/` produces the exact *SHA-256* fingerprint (`f91cf1076af52cf71dfb1b95aaf7ebb01c310d291c40c8d1ec64b613cd6abbf1`) committed in `plugin/veracrypt.mount.plg`.

**However, the audit found several real security weaknesses and bugs worth fixing before wider release:**
1. **Mount-location path checks can be bypassed** via trailing slashes, *symbolic links* (shortcuts pointing to another folder) in parent directories, and a delay between checking and mounting — allowing root to create folders or mount outside `/mnt/` (**S1**).
2. **Array stop and shutdown have real timeout and locking traps**: on Unraid's default 90-second shutdown timeout, the hooks' budgets are shorter than the plugin's own default container stop time (45s vs 60s) and too short for multiple busy volumes (22s), and a running unlock is never cancelled when the array stops (**S2**).
3. **Volume file paths are still unrestricted**: an earlier review restricted keyfiles to `/mnt/`, but never applied the same rule to volume files (**S3**).
4. **A subtle race in the new "Require HTTPS" check** means clicking Cancel at the wrong instant on plain HTTP can still send the password and mount the volume (**S4**).
5. **Forced dismount can stop unrelated Docker containers** (if they share a bind mount of `/mnt/user`) and can kill active Samba worker processes (**S5**).
6. **Privacy gap when log names are hidden**: process names holding a volume open are still written to the system log and archived notifications (**S6**).
7. **General bugs** include a JavaScript quirk where naming a volume `constructor` or `toString` permanently freezes its UI controls (**B1**), a revision conflict between the Volumes and Settings tabs on the same page (**B2**), wrong Unix permission bit math in `share_can_write()` (**B3**), and incomplete cleanup when Samba fails to reload or a dismount aborts (**B4**).

## S1. Medium-High: Mount location checks can be bypassed via trailing slashes, parent symbolic links, and a check-to-use delay

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `check_config()` (lines 215–225), `check_mount_point()` (lines 1194–1216), and `do_mount()` (lines 1253 and 1338–1362).
- **What could go wrong:**
  A *symbolic link* (often called a *symlink*) is a special file that acts like a shortcut pointing to another file or folder elsewhere on the server. When a program running as `root` follows a symlink without checking where it really points, it can accidentally modify sensitive system folders — a problem called *path traversal*.
  There are three gaps in how `mount_at` (the folder where a volume is mounted) is checked:
  1. **Parent symlinks are never checked:** `check_mount_point()` checks `is_link($point)` on the final folder only. Suppose a volume is configured to mount inside an Unraid share (for example `/mnt/user/myshare/sub/vault`), and a Docker container or network user with write access to `myshare` replaces `sub` with a symlink pointing to `/etc`. Because `vault` itself does not exist yet, `is_link()` returns false, and `do_mount()` then runs `mkdir(..., 0755, true)` and `mount` as `root`, creating a folder and mounting the volume inside `/etc` (completely outside `/mnt/`).
  2. **A trailing slash defeats `is_link()` and the "already mounted" check:** If `mount_at` is saved with a trailing `/` (for example `/mnt/user/myshare/link/`), PHP's `is_link()` follows the shortcut instead of testing the link itself and returns false. It also fails to match `/proc/mounts` (which never ends with `/`), bypassing the "already mounted" check.
  3. **Time-of-check to time-of-use (*TOCTOU*) race:** A *race condition* happens when the state of the system changes between the moment code checks a condition and the moment it acts on it. Here, `check_mount_point()` runs on line 1253, **before** `cryptsetup` unlocks the volume — which can take up to 3 minutes. During that window, another process or container with access to the parent share can replace the empty mount folder with a symlink or put files in it; `do_mount()` never checks again before running `mount` on line 1362.
  4. **No validation on save:** `check_config()` only checks that `mount_at` is text. It allows control characters, newlines, and paths outside `/mnt/` to be saved into `volumes.json` (only the browser script restricts it to `/mnt/user/`).
- **How likely:** Low to Medium. Requires mounting inside a shared folder (`MNT-2`) where another user or container can create symlinks, or a crafted `save-config` request.
- **How bad:** High if triggered — `root` creates directories or mounts an encrypted volume on top of an arbitrary system directory outside `/mnt/`.
- **Suggested fix:**
  1. Validate `mount_at` in `check_config()` too: reject trailing slashes, control characters (`\x00-\x1f`), `%`, trailing `\`, `..`, and paths outside `/mnt/addons/<name>` or `/mnt/user/...` (or whichever `/mnt/` roots you intend to allow).
  2. In `check_mount_point()`, strip/reject trailing slashes, walk up to the deepest existing ancestor folder, resolve it with `realpath()`, and verify that the resolved path still starts with `/mnt/` (and that no component along the path is a symlink).
  3. Call `check_mount_point($point)` a second time immediately before `mkdir` and `mount` (after `cryptsetup` finishes).

## S2. Medium: Array stop and shutdown can leave volumes unlocked, mounted, or cut off uncleanly

- **Confidence:** Confirmed by reading the code for the timeout mismatch, missing unlock cancellation, and abrupt `SIGTERM` exit. **Needs verification on the server** for whether PHP child processes inherit the open lock file descriptor.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/stopping_docker` (lines 36–51)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/unmounting_disks` (lines 36–51)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `DEFAULT_GRACE` (line 49), `FORCE_WAIT` (line 52), `take_lock()` (line 1132), `do_dismount()` (lines 1637–1725).
- **What could go wrong:**
  Three problems can combine during an array stop, reboot, or shutdown:
  1. **Default time budgets are shorter than the plugin's own defaults:** Unraid's default `shutdownTimeout` is 90 seconds. `stopping_docker` takes half of that (**45 seconds**), yet the plugin's own default grace period for a single container is **60 seconds** (`DEFAULT_GRACE = 60`). Even one stubborn container will exceed `stopping_docker`'s 45-second budget! Meanwhile `unmounting_disks` takes a quarter (**22 seconds**), yet forcing a single busy volume can take **12+ seconds** (`FORCE_WAIT = 10` seconds waiting for `SIGTERM` + 2 seconds after `SIGKILL`). With just two busy volumes, `timeout` kills `vcmount` partway through.
  2. **Killing `vcmount` mid-dismount leaves half-finished work:** When `timeout` expires, it sends `SIGTERM` (a stop signal). Unlike the password-check step, `do_dismount()` does not catch `SIGTERM`, so `vcmount` exits immediately — potentially after removing a share or unmounting a filesystem, **before** running `cryptsetup close` or touching remaining volumes. Unraid then fails to unmount the array disks (`target is busy`) and eventually forces a hard power-off with volumes still mounted (risking data corruption, especially on exFAT/NTFS).
  3. **An in-progress unlock blocks array stop completely:** Neither `stopping_docker` nor `unmounting_disks` calls `vcmount cancel-unlock`. If a slow unlock (for example a wrong large PIM, which runs up to 185 seconds) is in progress when the user stops the array or shuts down, both hooks keep getting result code 6 ("another `vcmount` action is still running") until their entire time budgets expire, leaving **every** mounted volume mounted!
  4. **Child processes may keep holding the lock file (needs server verification):** PHP's `fopen()` on Linux does not normally set the *close-on-exec* flag (`FD_CLOEXEC`, which tells the operating system to close a file automatically when starting a child program). When `timeout` kills `vcmount` during `stopping_docker`, its child `docker stop -t 60` keeps running and likely still holds the exclusive lock on `/var/run/vcmount.lock`, blocking `unmounting_disks` with code 6.
- **How likely:** Medium. Happens naturally with Unraid's default 90-second shutdown timeout whenever a dependent ignores `SIGTERM`, two volumes are busy at shutdown, or an unlock is running when the user stops the array.
- **How bad:** High — volumes can be left unlocked or mounted during a forced power-off, risking filesystem corruption and an unclean shutdown.
- **Suggested fix:**
  1. At the start of `unmounting_disks` (and optionally `stopping_docker`), call `$VCMOUNT cancel-unlock` if code 6 is seen and `vcmount busy` reports an active unlock, so a stuck unlock cannot block shutdown.
  2. Pass a remaining time budget to `dismount --all --array-stop` (or catch `SIGTERM` to finish `cryptsetup close` cleanly on the current volume before exiting) and shorten `FORCE_WAIT` when time is tight or signal all busy volumes' processes together instead of waiting 10 seconds sequentially per volume.
  3. On Bob, verify whether child processes inherit `/var/run/vcmount.lock` (`ls -l /proc/<child-pid>/fd` during a slow command). If so, avoid holding the lock file open across `proc_open` or use `timeout -k` / a process group kill so timed-out hooks also terminate their stuck child.
  4. Implement `LIFE-3` (warn in the Settings/Edit pages when total dependent grace periods exceed Unraid's `shutdownTimeout`).

## S3. Medium: Volume file paths (`file` / `--file`) are not restricted to `/mnt/` (incomplete K1 fix)

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/include/actions.php`: `mount-once` (lines 92–96)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `check_config()` (lines 210–213), `command_mount()` (line 1402), `do_mount()` (lines 1237–1240).
- **What could go wrong:**
  In the second security review (`docs/REVIEW-secrets.md`, finding **K1**), keyfile paths were restricted to `/mnt/` (checked both before and after resolving symlinks with `realpath()`), with a single generic refusal message. K1 explicitly noted *"Apply the same rule to `--file` in a later change"*, but that change was never made:
  1. **Blocking-file denial of service:** A logged-in web request (`mount-once` or `save-config` + `mount`) can point `file` at special system files such as `/proc/kmsg` (which PHP's `is_file()` considers a regular file, but which blocks indefinitely when read). `cryptsetup` then hangs for up to 185 seconds while holding the engine lock, blocking all mounts, dismounts, and array-stop hooks.
  2. **Arbitrary file probing (*existence oracle*):** An *existence oracle* is an error message that reveals whether hidden files exist on the server. Because `do_mount()` returns `"The volume file <path> does not exist or is not an ordinary file"` for missing files versus `"Could not unlock"` for existing ones, any path under `/boot`, `/etc`, or `/root` can be probed.
  3. **Attaching loop devices to arbitrary system files:** `cryptsetup tcryptOpen` as `root` will attach a Linux loop device to any regular file on the server (such as `/boot/config/super.dat` or `/etc/shadow`) before failing header decryption. (Because `cryptsetup` never writes VeraCrypt headers, it will not modify the file, but it should never touch files outside `/mnt/`.)
  4. **Missing control-character and length checks on saved `file` paths:** Unlike `mount-once` in `actions.php`, `check_config()` and CLI `command_mount()` do not check `strlen($file) <= 4096` or reject control characters (`\x00-\x1f`).
- **How likely:** Low (requires an already logged-in Unraid administrator or a malformed config file).
- **How bad:** Medium (engine lock denial of service, unnecessary `root` access to non-storage files).
- **Suggested fix:** Apply the exact same rule as `check_keyfiles()` to volume files: require `str_starts_with($file, '/mnt/')`, length <= 4096, and no control characters in `check_config()`, `actions.php`, `command_mount()`, and `vcmount.js`; after `realpath($file)` in `do_mount()`, require `str_starts_with($real, '/mnt/')` and return one uniform refusal message.

## S4. Medium: Clicking Cancel during the pre-send HTTPS check on plain HTTP still sends the password and mounts

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/js/vcmount.js`: `submitMount()` (lines 818–837) and `#vcm-cancel` click handler (lines 1429–1432).
- **What could go wrong:**
  To fix the stale-setting gap found in `docs/REVIEW-secrets.md` section 10, `submitMount()` over plain HTTP first sets `mounting = true` (line 824) and asks the server for the latest `require_https` setting via `freshHttpsSetting()`. During that brief network wait, the Mount button is not disabled and the Cancel button is still active.
  - Concrete scenario: You are on plain HTTP (with "Require HTTPS" switched off), type your password, click Mount, and immediately click Cancel (or press Escape) before the server answers the `list` check. Because `mounting` is `true`, the Cancel handler calls `cancelUnlock()` (which disables the Cancel button and changes it to `"Cancelling…"` and creates `/var/run/vcmount.cancel`). A fraction of a second later, `freshHttpsSetting()` returns, sets `mounting = false`, ignores `cancelling`, and calls `submitMount(null)` — **sending your password over plain HTTP and starting the mount**, while the Cancel button is stuck disabled so you cannot cancel the real unlock! (And `do_mount` line 1236 immediately deletes the early cancel marker.)
- **How likely:** Low (needs a click on Cancel within the brief round-trip of the `list` check, or when the server is slow to respond).
- **How bad:** Medium — the password is sent and the volume is mounted against the user's explicit Cancel click, and the Cancel control breaks for that unlock.
- **Suggested fix:** Use a separate flag or request counter (for example `checkingHttp`) during `freshHttpsSetting()`. Disable the Mount button while checking, and if the user clicks Cancel during the check, abort the pending submit, clear `#vcm-password` and `#vcm-pim`, and close the dialog instead of calling `cancelUnlock()`.

## S5. Medium: Forced dismount can stop unrelated Docker containers and kill Samba worker processes

- **Confidence:** Confirmed by reading the code. Exact container mount propagation depends on how individual Unraid templates configure bind mounts (**needs verification on the server** if you use `MNT-2`).
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `mount_users()` (lines 1533–1567), `end_programs()` (lines 1587–1625), and `do_dismount()` (lines 1657–1711).
- **What could go wrong:**
  1. **Stopping unrelated Docker containers:** On Unraid, many containers (media servers, backup tools, file managers) are given access to `/mnt/user`. When a VeraCrypt volume is mounted inside a user share (`MNT-2`, e.g. `/mnt/user/data/secret`), Linux can copy that mount entry into the *mount namespace* (each container's private view of mounted folders) of every running container that mounted `/mnt/user`. Later, during `dismount --force`, `mount_users()` scans `/proc/*/mountinfo` for the volume's device number and runs `docker stop -t 10` on **every** container that has that entry — stopping and killing unrelated containers (such as a database or backup job) with only a 10-second warning, even though they were never listed as dependents!
  2. **Killing active Samba (`smbd`) workers:** `remove_share()` runs `smbcontrol all close-share <name>`, which works asynchronously (it asks Samba workers to disconnect and returns immediately). If `umount` runs before `smbd` finishes closing the file — or if a Windows PC has the volume open through a parent Unraid user share (`MNT-2`), which `remove_share()` never closes — `holders()` finds `smbd`, and `end_programs()` sends `SIGTERM` and `SIGKILL` to `smbd`. Because Samba uses one worker process per client connection, this abruptly drops **all** other Unraid shares that computer had open.
  3. **Process-ID reuse and zombie processes:** `end_programs()` collects numeric process IDs (*PIDs*), sends `SIGTERM`, waits up to 10 seconds, checks only `is_dir("/proc/$pid")`, and then sends `SIGKILL`. If a process dies and Linux reuses its PID within those 10 seconds, `SIGKILL` hits an unrelated new process. If a process dies and remains a *zombie* (a finished process waiting for its parent to collect its exit status), `is_dir("/proc/$pid")` stays true and wastes the full 12-second wait.
  4. **Overly broad cgroup matching:** `mount_users()` line 1552 treats any 64-character hex string in `/proc/<pid>/cgroup` as a Docker container ID, rather than checking specifically for a Docker cgroup path.
- **How likely:** Medium when `--force` is used alongside `MNT-2` (mounting inside a share) or active SMB clients. Low for PID reuse.
- **How bad:** Medium — unexpected forced stop/kill of unrelated containers or dropped SMB sessions across other shares.
- **Suggested fix:**
  1. After `smbcontrol all close-share`, wait briefly (for example retry `umount` for up to 2 seconds) before concluding the volume is busy.
  2. In `end_programs()`, record each process's start time from `/proc/<pid>/stat` (field 22) and skip zombies (`state === 'Z'`) before sending `SIGKILL`, so a recycled PID can never be killed.
  3. Match Docker cgroups more specifically (e.g. `docker[-/][0-9a-f]{64}`), and in the "Force dismount" confirmation dialog, consider warning specifically about unrelated containers when `mount_at` is inside `/mnt/user/`.

## S6. Medium-Low: Privacy leak when "Show volume names in logs" is off — process names still reach syslog and flash notifications

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `log_event()` (lines 604–631) and `do_dismount()` (lines 1662 and 1678–1679).
- **What could go wrong:**
  By default, `"Show volume names in logs"` is OFF (`PRIV-1`) so that Unraid's system log (which is copied to the flash drive at shutdown and included in diagnostics) and Unraid's archived notifications (`/boot/config/plugins/dynamix/notifications/archive/`) do not reveal your volumes or apps. `log_event()` enforces this by replacing any text inside double quotes (`"..."`) with `(name hidden)`.
  - Concrete scenario: A dismount of a saved volume is aborted because a program is using it, or is forced to end programs. Lines 1662 and 1679 pass `implode(', ', $ended)` / `implode(', ', $programs)` (for example `paperless (process 4123)` or `qbittorrent (process 892)`) **without double quotes** into `log_event(..., true)`. As a result, `log_event()` hides the volume name, **but writes the program names straight into syslog and into permanent notification archives on the flash drive**.
  - Additionally, any process on Linux can set its own `/proc/<pid>/comm` name (up to 15 bytes) to arbitrary characters including double quotes or HTML markup. While `vcmount.js` safely escapes it with `esc()`, it is passed unstripped to Unraid's `notify` script (`NOTIFY_SCRIPT -d $message`). Whether Unraid's notification viewer escapes `-d` **needs verification on the server**.
- **How likely:** Certain whenever a saved volume has a busy or forced dismount while `log_names` is off.
- **How bad:** Low-Medium — leaks the names of programs using your encrypted volumes to persistent logs/flash backups, contrary to `PRIV-1`.
- **Suggested fix:** When `log_names` is off, omit process names from syslog and notifications (or put each process label inside double quotes so `log_event()` hides them). Also strip control characters and quotes when reading `/proc/<pid>/comm` in `program_label()`.

## S7. Medium-Low: Race conditions in `fix-top` and `fix-permissions` (misordered or missing engine lock)

- **Confidence:** Confirmed by reading the code. Exact behaviour of Unraid's `/usr/local/sbin/newperms` with symlinks or special characters in folder names **needs verification on the server**.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `command_fix_top()` (lines 2295–2308) and `command_fix_permissions()` (lines 2318–2334).
- **What could go wrong:**
  1. In `command_fix_top()`, `owner_fs_point($args[0])` checks that the volume is mounted at `$point` **before** calling `take_lock()` on the next line. If a dismount finishes in the instant between lines 2300 and 2301, `take_lock()` succeeds and `chown nobody:users` + `chmod 0777` (world-writable) runs on the now-unmounted directory `$point` (for example a folder inside `/mnt/user/<share>`).
  2. `command_fix_permissions()` does not take the engine lock at all, and launches Unraid's `/usr/local/sbin/newperms` in the background (`sh -c 'exec "$0" "$1" ... &'`). Note that `$tool` and `$point` are passed safely as positional arguments (so there is **no shell injection**), **but** if the volume is dismounted while `newperms` is starting, `newperms` can recursively rewrite permissions on the underlying unmounted folder. You can also start multiple overlapping `newperms` runs on the same volume at once.
- **How likely:** Low (needs a concurrent dismount and permission-fix click).
- **How bad:** Medium — sets world-writable (`0777`) permissions on the wrong folder, or starts recursive permission changes outside the mounted volume.
- **Suggested fix:** Call `take_lock()` *before* `owner_fs_point()` in `command_fix_top()`. In `command_fix_permissions()`, take the lock before `owner_fs_point()` and verify the mount is still active right before spawning `newperms` (and track/prevent duplicate concurrent `newperms` runs if desired). Also check `/usr/local/sbin/newperms` on Bob to verify it handles spaces/special characters in `$1` and does not follow symlinks out of `$point`.

## S8. Medium-Low: Plugin update deletes the old package before verifying the new download, and `.plg` deviates from `LIFE-6`

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `plugin/veracrypt.mount.plg` (lines 30–46 and 59–81)
  - `.github/workflows/release.yml` (lines 18–48)
  - `scripts/build.py` (lines 112–182).
- **What could go wrong:**
  1. **Old package deleted before new package is verified:** Lines 31–39 of `veracrypt.mount.plg` delete all older `veracrypt.mount-*.txz` files from `/boot/config/plugins/veracrypt.mount/` **before** lines 43–46 download and SHA-256-verify the new `.txz`. If the download fails (offline, GitHub error, or a tampered `.txz` rejected by SHA-256), the previous working package on the flash drive has already been deleted, which can break reinstalling the plugin on the next offline reboot.
  2. **Deviation from `SPEC.md` `LIFE-6`:** `SPEC.md` requires refusing both updates and removals while volumes are mounted, without auto-dismounting. In practice:
     - **Update** does not check for mounted volumes or an active engine lock at all (updating during an active unlock/dismount replaces the files underneath it).
     - **Removal** runs `vcmount dismount --all`, which *does* automatically dismount mounted volumes and stop/kill their dependent containers before checking whether any volume is busy. If volume 1 succeeds and volume 2 is busy, volume 1 has already been dismounted and volume 2's share/dependents stopped before removal aborts.
  3. **Could a tampered package be installed? (Release pipeline assessment):**
     - Replacing a `.txz` asset in GitHub Releases **alone** cannot trick Unraid into installing it, because `veracrypt.mount.plg` pins the exact `<SHA256>` hash and `.github/workflows/release.yml` refuses to publish unless a fresh reproducible build matches the committed `.plg` (`build.py --check`).
     - **Platform limit:** Unraid's plugin manager fetches `.plg` over HTTPS from `main`, and does not support cryptographic signatures (like GPG or Sigstore) on `.plg` files. ## What Was Checked and Found Sound (Security)

- **Password & PIM secrecy (`SEC-1`):** Neither the password nor the PIM ever touches a command line, environment variable, file, log, notification, error message, browser storage (`localStorage`/`sessionStorage`), `console.*`, or HTTP response. `vcmount` never even reads them into its own memory — `cryptsetup` reads them directly from standard input.
- **No shell interpolation (`SEC-3`):** Every external program call in `include/actions.php` and `scripts/vcmount` uses `proc_open()` with an array of arguments (no shell). The single `sh -c` call in `command_fix_permissions()` passes `$tool` and `$point` as quoted positional arguments (`"$0" "$1"`), not interpolated strings.
- **Option injection resistance:** Volume names (`NAME_PATTERN`), container names (`CONTAINER_PATTERN`), usernames (`USER_PATTERN`), revisions, and paths (all starting with `/`) cannot begin with `-`, preventing option injection into `cryptsetup`, `mount`, `umount`, `smbcontrol`, `docker`, `blkid`, and `kill`.
- **Web authentication, CSRF, and XSS (`SEC-2`):** `action.php` accepts only `POST`, sets `Cache-Control: no-store`, strips `$_POST`/`$_REQUEST`, and relies on Unraid's `local_prepend.php` (confirmed on Bob in `REVIEW-secrets.md` 7.1). In `vcmount.js` and `vcsettings.js`, dynamic values are consistently rendered via `.text()`, `.val()`, `.attr()`, or `esc()`, preventing *cross-site scripting (XSS)* (injecting malicious scripts into the web page).
- **Cancel-unlock safety:** `cancel-unlock` takes no parameters and only writes a fixed empty marker; only the waiting mount kills its own uncollected `cryptsetup` child, with `SIGCHLD` set to default and signal handlers restored in `finally`.
- **Header safety (`SEC-7`):** The engine only calls `cryptsetup` with `tcryptOpen`, `close`, and `status` — never any command that writes VeraCrypt headers.
- **Reproducible build and release integrity:** `scripts/build.py` strips `dev-only` blocks, enforces root ownership, fixed permissions, LF line endings, and deterministic timestamps, refuses forbidden filenames (`volumes.json`, `.secrets`, `throwaway`), and matches `plugin/veracrypt.mount.plg`'s SHA-256 byte-for-byte. `.github/workflows/release.yml` pins `actions/checkout` to a full 40-character commit hash, sets `persist-credentials: false`, uses minimal `contents: write` permissions, and runs `python3 -I scripts/build.py --check`.
- **Config file secrecy (`SEC-4`):** `volumes.json` on `/boot` stores no passwords, no PIM values, and no keyfile contents.

## B3. Medium-High (Confirmed): `share_can_write()` evaluates Unix file permissions incorrectly

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `share_can_write()` (lines 2239–2249).
- **What goes wrong:**
  ```php
  return ($st['uid'] === SHARE_UID && ($mode & 0300) === 0300)
      || ($st['gid'] === SHARE_GID && ($mode & 0030) === 0030)
      || ($mode & 0003) === 0003;
  ```
  Linux checks permissions in strict order: if the owner matches `nobody` (UID 99), Linux checks **only** the owner bits and ignores group/other bits. Because this code uses `||` (OR), a folder owned by `nobody` with mode `0577` (owner cannot write, other can) falsely returns `true`, so the plugin never offers `"Let the share write"` even though SMB writes fail. The same happens for group `users` with mode `0757`. It also checks `0300`/`0030`/`0003` (write + execute), forgetting the read bit (`4`), which Samba needs to list the folder.
- **How likely:** Low-Medium (appears on ext4/XFS/Btrfs volumes with non-default top-folder permissions).
- **How bad:** Medium — prevents the plugin from noticing that a share cannot write or browse.
- **Suggested fix:** Use `if ($st['uid'] === SHARE_UID) return ($mode & 0700) === 0700; if ($st['gid'] === SHARE_GID) return ($mode & 0070) === 0070; return ($mode & 0007) === 0007;`.

## B6. Medium (Confirmed): `vcm_run()` writes stdin in one unchecked `fwrite()` and lacks a `SIGKILL` timeout fallback

## B7. Medium (Confirmed): `holders()` misses memory-mapped files and running binaries, and `remove_share()` doesn't wait for `smbd` to release files

## B11. Medium (Confirmed): Agreed Docker/lifecycle safeguards (`DOC-6`, `DOC-7`, `LIFE-3`) are not built yet, causing practical Unraid pitfalls

- **Where:** `docs/SPEC.md` (`DOC-6`, `DOC-7`, `LIFE-3`) vs `scripts/vcmount` and `js/vcmount.js`.
- **What goes wrong:**
  - If a user forgets to disable Unraid autostart or a Docker restart policy (`always` / `unless-stopped`) on a dependent container, Docker starts it at boot **while the volume is locked**. Docker then creates `/mnt/addons/<name>` in RAM and the container writes data into it. When the user later tries to mount the volume, `check_mount_point()` **refuses** because `/mnt/addons/<name>` is not empty — and any data written by the container is lost on reboot.
  - There is no warning when the sum of dependent grace periods exceeds Unraid's `shutdownTimeout` (see also **S2**).
- **How likely:** High for new users setting up dependents.
- **How bad:** Medium — mounts fail mysteriously after reboot and containers write to RAM instead of the volume.
- **Suggested fix:** Implement `DOC-7` (check `/var/lib/docker/unraid-autostart` and `docker inspect` `HostConfig.RestartPolicy.Name`) and `LIFE-3` (compare total grace time against `shutdownTimeout` in `/var/local/emhttp/var.ini`) and show warnings in the Edit panel.

## B12. Medium (Confirmed): `stop_dependents()` falsely reports slow clean stops as "killed", and forced container stop ignores errors

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `stop_dependents()` (lines 847–862) and `do_dismount()` (lines 1699–1706).

## B13. Medium-Low (Confirmed): Multi-byte UTF-8 length mismatches (`password`, `display_name`) and unvalidated "Mount once" inputs

- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/include/actions.php` (line 79)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount` (line 217)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/js/vcmount.js`: `submitMount()` (lines 843–888).
- **What goes wrong:**
  1. *UTF-8 bytes vs characters:* In text encoding (*UTF-8*), English letters take 1 byte, while accented letters (`ü`, `é`) take 2 bytes and emoji/Asian characters take 3–4 bytes. `actions.php` checks `mb_strlen($password, 'UTF-8') > 128` (characters), whereas VeraCrypt limits passwords to **128 bytes** (64 bytes in older VeraCrypt). A 100-character non-ASCII password passes PHP's check and fails with `"wrong password"`.
  2. Conversely, `check_config()` checks `strlen($display) > 100` (**bytes**), while the HTML input has `maxlength="100"` (**characters**). Typing 60 German/emoji characters is allowed by the text box, then rejected on save with `"display name or mount location that is not valid"`.
  3. In "Mount a file once", `submitMount()` does not validate `#vcm-file` or `#vcm-name` before reading and wiping the password field and sending the request to the server — so forgetting to fill in the name clears your password and forces you to retype it.
- **How likely:** Low-Medium (for non-ASCII text or forgetting a field in "Mount once").
- **How bad:** Low — annoying validation errors and retyping passwords.
- **Suggested fix:** Check `strlen($password) > 128` (bytes) in `actions.php`, use `mb_strlen($display, 'UTF-8') > 100` in `check_config()`, and validate `data.name` and `data.file` in `submitMount()` before reading/clearing the password field.

## B14. Medium-Low (Suspected — needs test on the server): Copied XFS/Btrfs volumes hit duplicate-UUID errors, and `blkid` may return cached types

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `do_mount()` (lines 1319 and 1362–1383).
- **What goes wrong:**
  1. `README.md` advises users to *"Try it with a copy of a volume before you trust it with your only one."* Every XFS and Btrfs filesystem has a unique ID (*UUID*). If a user tries to mount both a volume and its copy at the same time, Linux refuses to mount the second XFS volume (`Filesystem has duplicate UUID`) — and on Btrfs, two identical UUIDs can cause mount failures or kernel confusion. Meanwhile `do_mount()` tells the user to run `xfs_repair` or `btrfs check`, which is the wrong advice for a duplicate UUID.
  2. Line 1319 runs `blkid -o value -s TYPE $device` without `-p` (low-level probe). Depending on Unraid's `blkid` cache configuration, reusing the same volume name (e.g. via "Mount a file once") for a different filesystem could read a stale cached filesystem type from `/run/blkid/blkid.tab`.
- **How likely:** Low-Medium when testing with copies of XFS/Btrfs volumes.
- **How bad:** Medium (confusing repair advice; Btrfs duplicate-UUID risk).
- **Suggested fix:** Pass `-p` (or `-c /dev/null`) to `blkid`, detect duplicate-UUID errors in `mount`'s stderr with a clear explanation, and warn in `README.md` not to mount an XFS/Btrfs volume and its copy simultaneously.
