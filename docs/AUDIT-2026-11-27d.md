## F1. Medium: Two-round forced `dismount --all` (`force_busy_volumes()`) misreports failed/skipped container stops, skips timeout logging, and fires a spurious round-1 alert

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `do_dismount()` (line 2452), `force_busy_volumes()` (lines 2500–2549).
- **What could go wrong:**
  The new two-round forced `dismount --all` (S1.4) works well for the happy path (three busy volumes with stubborn host processes sharing one wait), **but has four concrete logic/logging flaws on failure and edge paths**:
  1. **Unconditionally logs and reports containers as stopped even if `docker stop` failed or never ran (regression of Audit 1 `B12`):**
     Lines 2509–2512 run `docker stop` only when `$containers !== [] && !out_of_time(5)` and **discard the return value of `run()`**. Then lines 2528–2533 unconditionally execute:
     ```php
     if (($stopped[$name] ?? []) !== []) {
         $notes[] = 'Forced: stopped ' . implode(', ', array_map(fn($c) => "\"$c\"", $stopped[$name])) . '.';
         if ($volume !== null) {
             log_event("dismount of \"$name\" forced: stopped " . implode(', ', array_map(fn($c) => "\"$c\"", $stopped[$name])), true);
         }
     }
     ```
     If `out_of_time(5)` was true (so `docker stop` **never ran at all**), or if `docker stop` failed (e.g. Docker daemon busy/unresponsive), the engine still writes a warning notification and syslog entry claiming `"dismount of \"<name>\" forced: stopped \"container <c>\""`.
  2. **Still stops containers when `end_programs()` refused the command:**
     If `vcmount dismount --all --force` was started from inside one of the volumes, `end_programs()` throws `CODE_REFUSED` (caught on line 2505 into `$refused`), **but line 2509 still proceeds to run `docker stop` on `$containers`** before line 2536 re-throws `$refused`.
  3. **Spurious round-1 `"could not be locked"` alert when a container holds a mount namespace:**
     In round 1 (`$first_pass === true`), if `umount` succeeds on a volume but `cryptsetup close` fails because a non-dependent container still holds the device in its mount namespace (`mount_users()`), `do_dismount()` line 2452 checks `if ($saved)` **without `&& !$first_pass`** (unlike lines 2346 and 2420). It immediately writes a warning notification `"\"<name>\" was dismounted but could not be locked"` even though round 2 immediately follows and locks it. (Also, round 2 does not batch `mount_users()` containers across volumes — it handles them sequentially inside `do_dismount(..., true)`.)
  4. **Silent timeout in round 2 under `unmounting_disks`:**
     When round 2 hits `out_of_time(2)` on line 2539, it throws `Fail("\"$name\" was left mounted: no time was left.", CODE_BUSY)` which is caught on line 2545 — **without calling `log_event()` for saved volumes** (unlike round 1's `out_of_time(5)` on line 2611). Because `unmounting_disks` redirects stdout and stderr to `/dev/null`, neither syslog nor Unraid notifications name which volume was left mounted.
- **How likely:** Low on normal array stops (Docker is already stopped before `unmounting_disks` runs); Medium for manual `vcmount dismount --all --force` or tight shutdown budgets with busy volumes.
- **How bad:** Medium — false `"forced: stopped"` notifications, spurious warnings, or missing syslog/notification identification of a volume left mounted at shutdown.
- **Suggested fix:**
  1. In `force_busy_volumes()`, skip `docker stop` if `$refused !== null`; track which container IDs actually stopped (`$r['code'] === 0` or `container_running($id) === false`) and only report/log those as stopped (reporting failures as `"Could not stop ..."` like `force_stop_containers()`).
  2. On line 2452 of `do_dismount()`, change `if ($saved)` to `if ($saved && !$first_pass)`.
  3. On line 2539–2541 of `force_busy_volumes()`, log `"dismount of \"$name\" was not finished: no time was left"` via `log_event(..., true)` when `$volume !== null`.

## F2. Medium-Low: `restore_after_busy()` restarts dependents that were intentionally stopped beforehand, and `README.md` overstates `"nothing is changed"` for local-holder busy dismounts

- **Confidence:** Confirmed by reading `scripts/vcmount` and `README.md`.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `do_dismount()` (lines 2363, 2408–2411), `restore_after_busy()` (lines 2558–2574)
  - `README.md` (lines 49–51).
- **What could go wrong:**
  1. **Starting containers that were already stopped:**
     When a local program holds a volume open during a normal (non-forced) dismount, `do_dismount()` calls `stop_dependents()` (line 2363) — which stops only the dependents that are *currently running* and returns their results — then hits `umount` busy, and calls `restore_after_busy()` (line 2410). `restore_after_busy()` passes the full `$volume['dependents']` list to `start_dependents()`, which **starts every configured dependent, including any container the user had intentionally stopped before clicking Dismount** (e.g. for maintenance or troubleshooting). It also sleeps through every configured `delay` (up to 600 s per dependent) before returning the `"still in use"` popup to the WebUI.
  2. **Promise mismatch in `README.md` (lines 49–51):**
     `README.md` states: *"A normal dismount never takes a volume away from a program or a computer that still uses it, a file open over the network included: it stops and says who holds it, and nothing is changed."*
     - For a **file open over SMB**, this is 100% accurate (refused at line 2329 before removing the share or stopping dependents).
     - For a **local program** (e.g. an SSH shell or local backup process), `do_dismount()` *first* disconnects SMB clients (`remove_share()`) and stops (and potentially **kills** after its grace period!) every running dependent container, and only then restores the share and restarts the dependents. Saying *"nothing is changed"* overstates the local-holder case.
- **How likely:** Low-Medium whenever a user has a stopped dependent or a local process holding a volume during normal dismount.
- **How bad:** Low-Medium — unexpectedly starting a stopped container, unexpected container restarts/kills, or long UI wait before the busy dialog appears.
- **Suggested fix:**
  1. Pass the list of dependents that `stop_dependents()` actually stopped (i.e. `$stopped_names = array_column($dep_results, 'container')`) into `restore_after_busy()`, and filter `$volume['dependents']` to only those containers.
  2. Soften `README.md` line 51 to note that for a local program holding a volume after its dependents stop, the volume stays mounted and its share and dependents are put back (or check non-dependent local `holders()` before stopping dependents when `!$force`).

## F3. Low: `/run/vcmount/stop` is never cleared after Docker/array stop (NTP backward clock step hazard)

- **Confidence:** Confirmed by reading `scripts/vcmount`, `event/stopping_docker`, `event/unmounting_disks`, and `event/docker_started`.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `stop_requested()` (lines 991–1000), `command_cancel_unlock()` (line 3639)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/docker_started` (lines 31–42).
- **What could go wrong:**
  1. `cancel-unlock --array-stop` writes `time()` to `/run/vcmount/stop`, and `stop_requested()` returns `true` whenever `(int) trim($asked) >= $GLOBALS['vcm_started']`. Nothing ever removes `/run/vcmount/stop` (until reboot or plugin removal). If Docker is toggled off in Settings -> Docker while `vcmount` is busy (writing `/run/vcmount/stop`), and the server's clock later steps backward (e.g. NTP correcting a fast clock), `/run/vcmount/stop` holds a future timestamp — causing `stop_requested()` to return `true` on every subsequent `vcmount` run until wall-clock time passes that timestamp, silently disabling `start_dependents()`, `stray_dependents()`, `command_idle_check()`, and `restore_after_busy()`.
  2. Minor timing edge: if `docker_started` is sleeping in its 5-second `WAIT=5` retry loop when `stopping_docker` finishes, `docker_started` wakes up with a fresh `vcmount start-dependents --all` whose `$GLOBALS['vcm_started']` is newer than `/run/vcmount/stop` and briefly attempts to start dependents while Unraid is stopping Docker (low impact since Unraid stops Docker immediately after `stopping_docker`).
- **How likely:** Very Low (requires a clock step backward after a Docker-stop lock collision).
- **How bad:** Low-Medium — silently disables idle lock, stray-dependent protection, and dependent startup until the clock catches up or reboot.
- **Suggested fix:** Remove `/run/vcmount/stop` at the end of `stopping_docker` / `unmounting_disks` (or ignore timestamps in `STOP_FILE` that are in the future relative to `time()`, e.g., `$ts <= time() && $ts >= $GLOBALS['vcm_started']`).

## F5. Low (Confirmed): `volume_log_lines()` hides legitimate dependent logs when a container shares its volume's name and uses the wrong quote pattern for containers

- **Where:** `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `volume_log_lines()` (lines 3853–3854).
- **What could go wrong:**
  ```php
  if (strpos($line, 'veracrypt.mount') !== false && strpos($line, $needle) !== false
      && strpos($line, 'dependent ' . $needle) === false && strpos($line, 'container ' . $needle) === false) {
  ```
  1. If a volume named `nextcloud` has a dependent container also named `nextcloud` (a very common naming pattern), log lines such as `dependent "nextcloud" of "nextcloud" could not be started` or `dependent "nextcloud" of "nextcloud" did not stop within 10 seconds and was killed` match `strpos($line, 'dependent "nextcloud"') !== false` — so **the volume's own dependent errors and kills are hidden from its Volume Information log view**.
  2. Forced container-stop log lines format the container label as `dismount of "vol" forced: stopped "container foo"` (lines 2166, 2231 — quote *before* `container`).
