## Executive Summary

**Overall pre-release verdict: Strong core security architecture — no critical or high-severity secret leaks, no shell injection, and no unauthenticated takeover paths. Ready for Community Applications after fixing a small set of Medium pre-release items and cutting a fresh release build.**

What makes the core architecture trustworthy for strangers installing it from Community Applications:
- **Secret handling (`SEC-1`) holds end-to-end:** Passwords and *PIMs* (VeraCrypt's Personal Iterations Multiplier) never appear in command-line arguments, environment variables, files, logs, notifications, error messages, browser storage, or HTTP responses. `vcmount` never reads them; `cryptsetup` reads them straight from *standard input* (a private pipe).
- **No shell interpolation (`SEC-3`):** Every external binary in `include/actions.php` and `scripts/vcmount` is executed directly via `proc_open()` with fixed argument arrays and absolute system paths (`program()`). The single `sh -c` invocation (`command_fix_permissions()`) passes arguments via positional `"$0" "$1"` rather than string interpolation.
- **Web protection (`SEC-2`):** `include/action.php` accepts `POST` only, sets `Cache-Control: no-store`, catches all `\Throwable` with a fixed message, relies on Unraid's login wall and `local_prepend.php` CSRF enforcement, and requires HTTPS by default (`require_https: true`) with fresh server checks before offering or submitting a password field.
- **Path & runtime hardening from earlier audits is in place:** Volume files and keyfiles are confined to `/mnt/` before and after `realpath()`; mount locations are validated for plain `/mnt/addons/...` or `/mnt/user/<share>/<folder>` paths with parent-symlink walking before and after unlock; runtime files live in root-only `/var/run/vcmount/` (`0700`, files `0600`, atomic temp-and-rename); cancel markers carry per-unlock opaque tokens; and `scripts/build.py` strips all `dev-only` blocks and produces reproducible `.txz` packages (verified byte-for-byte against `d6fef06` / `2026.11.27q`).
- **Clean git history:** Zero passwords, private keys, API tokens, private IP addresses, or personal e-mail addresses across all 39 commits.

**However, this full pre-release audit found concrete security, reliability, and documentation issues that should be addressed before listing in Community Applications:**

1. **Array-stop / shutdown reliability traps remain (`S1`, Medium):**
   - A one-shot `cancelled=no` guard in `stopping_docker` and `unmounting_disks` misses an unlock that holds the lock *before* `UNLOCKING_FILE` is written (for example during `smbstatus`), leaving the hook spinning on code 6 until its budget expires.
   - Cron (`vcmount check`) and background `docker_started` can hold `/var/run/vcmount/lock` across an array stop without being cancellable (`command_idle_check()` never rechecks `array_started()` between volumes, and `start-dependents` sleeps through `delay` without checking `array_started()`).
   - `do_dismount()` burns 2 seconds per busy volume on Samba `umount` retries even after Samba is stopped, and `unmounting_disks` (22 s default budget) handles busy volumes sequentially — so 3+ busy volumes can be skipped and left mounted at forced power-off.
2. **`.plg` install/update/removal gaps and unreleased `HEAD` (`S2`, Medium):**
   - `HEAD` (`b69c8f6`) changed `scripts/vcmount` after release `2026.11.27q` (`d6fef06`), so `plugin/veracrypt.mount.plg`'s SHA-256 does not match `HEAD` yet (must rebuild before tagging).
   - Plugin **update** performs no mounted-volume or active-lock check (`SPEC.md` `LIFE-6` gap).
   - Plugin **removal** partially dismounts earlier volumes and tears down a busy volume's share and dependents before aborting (contradicting both `SPEC.md` `LIFE-6` and the plain reading of `README.md`'s *"nothing is taken away"*), misreports non-busy exit codes (e.g. code 1) as *"still mounted and in use"* (blocking removal of a broken install), and has a narrow cron race between `dismount --all` and `update_cron`.
3. **Forced dismount can still disrupt unrelated containers and active SMB sessions (`S3`, Medium):** `holders()` does not filter out container processes (so 1:1 bind mounts such as `/mnt/user:/mnt/user` get killed directly via `kill` instead of `docker stop`), `mount_users()` stops unrelated containers that received `MNT-2` mount propagation, and `MNT-2` volumes accessed via a parent Unraid share cause `end_programs()` to kill `smbd` workers (dropping other shares for that client).
4. **Unsaved ("Mount a file once") privacy leak on array-stop timeout (`S4`, Medium-Low):** `dismount_all()` line 2295 calls `log_event(..., isset($config[$name]))`, passing `$saved` as `$notify` instead of skipping `log_event()` — writing unsaved volumes (and their names when `log_names` is on) to syslog, violating `PRIV-2` and `README.md`.
5. **Root path & permission-tool edges (`S5`, Medium-Low):** `valid_mount_at()` allows a typo in `/mnt/user/<nonexistent>/<folder>` to `mkdir` a brand-new top-level Unraid user share as `root`; `command_fix_permissions()` releases the engine lock immediately after spawning `newperms` in the background (allowing overlapping runs or concurrent dismounts); `user_exists()` still accepts system accounts (UID < 1000); and `check_mount_point()` does not call `clearstatcache(true)` before its post-unlock re-check.
6. **Secret memory-clearing fix (`AUDIT-2026-11-27b` S3) is ineffective in PHP (`S6`, Low):** Setting `$stdin = null` inside `vcm_run()` only drops one copy-on-write reference; `action.php`'s `$post`, `vcm_handle()`'s `$post`, and `vcm_handle()`'s `$stdin` keep the plaintext password and PIM alive in PHP-FPM memory for the full 180–300 s unlock wait.
7. **Documentation and `SECURITY.md` gaps (`S7`, Medium-Low + Part 3):** `SECURITY.md` does not exist; `README.md` omits the per-minute root cron job, idle auto-lock (`LIFE-8`), and automatic stopping of stray dependents (`DOC-6`), and overpromises on removal rollback, NFS double-use protection, File Activity coverage for "Mount once", and `"Mount once"` trace-freeness.
8. **Functional bugs (`Part 2`):** Clicking **Skip** during `"Mount all"` while unlocking is in progress corrupts the mount dialog and queue (**B1**, Medium-High); aborted non-forced dismounts leave SMB shares dead and dependents stopped without telling the user (**B2**, Medium); and both automated server test scripts (`tests/actiontest-on-bob.php` and `tests/enginetest-on-bob.sh`) are broken against current `main` (**B3**, Medium).

## S1. Medium: Array-stop and shutdown hooks still have an unlock-cancel race, cron/Docker-start lock contention, and multi-volume budget exhaustion

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/stopping_docker` (lines 38–63)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/unmounting_disks` (lines 38–63)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/event/docker_started` (lines 31–54)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `do_mount()` (lines 1506–1558), `do_dismount()` (lines 2175–2182), `dismount_all()` (lines 2288–2297), `command_start_dependents()` (lines 2426–2443), `start_dependents()` (lines 943–945), `command_idle_check()` (lines 2985–3023), `command_cancel_unlock()` (lines 3299–3311).
- **What could go wrong:**
  Although `--within`, `timeout -k 15`, close-on-exec (`'ce'`), and `cancel-unlock` closed the biggest gaps from the first audit, four realistic failure modes remain during array stop, shutdown, or reboot:
  1. **One-shot `cancel-unlock` race misses an unlock that has not yet written `UNLOCKING_FILE`:**
     In both `stopping_docker` and `unmounting_disks` (lines 56–62), when `vcmount` returns code 6 (*another action is running*), the hook runs `$VCMOUNT cancel-unlock` **once** and sets `cancelled=yes`. Between `take_lock()` (line 1862) and `write_marker(UNLOCKING_FILE, ...)` (line 1556), `do_mount()` runs `realpath()`, `check_keyfiles()`, `file_in_use()`, `check_mount_point()`, and `network_open()` (which forks `smbstatus -L --json`). If the hook hits code 6 during that window, `command_cancel_unlock()` finds no `UNLOCKING_FILE`, does nothing, and the hook sets `cancelled=yes` — so once `cryptsetup` starts a fraction of a second later (for up to 180 s), the hook **never calls `cancel-unlock` again** and spins until its entire budget expires, leaving every volume mounted.
  2. **Cron (`vcmount check`) and background `docker_started` can lock out array stop:**
     - If cron starts `vcmount check` seconds before the user clicks Stop Array or Shutdown, `stray_dependents()` (holding the lock for up to `grace + 30` s per container) or `command_idle_check()` (running `do_dismount()` sequentially across idle volumes) holds `/var/run/vcmount/lock`. Unlike `stray_dependents()` (which checks `if (!array_started()) break;` on line 3214), **`command_idle_check()` never checks `array_started()` inside its volume loop**. Because `cancel-unlock` only affects `cryptsetup`, the array-stop hooks spin on code 6 until they time out.
     - Similarly, `event/docker_started` runs `vcmount start-dependents --all` in the background (`BUDGET=300`), holding the lock while `start_dependents()` sleeps up to 600 s per `delay` without checking `array_started()` or deferring signals. Stopping Docker or the array shortly after starting Docker hits code 6 until those delays finish.
  3. **Wasted 2-second Samba `umount` retries and sequential busy waits exhaust the 22-second `unmounting_disks` budget:**
     On Unraid's default 90-second `shutdownTimeout`, `unmounting_disks` gets `budget = 22` s. Inside `do_dismount()` (lines 2175–2182), every failed `umount` retries 4 times with `usleep(500000)` (**2 full seconds**) to let Samba close shares — **even when Samba is already stopped** (as it always is during `unmounting_disks`) or when the volume had no share. With `FORCE_WAIT = 10` s + 2 s `SIGKILL` wait per stubborn volume, each busy volume consumes up to 14 s sequentially; with 3 busy volumes, the third hits `out_of_time(5)` and is left mounted, causing Unraid to hit `target is busy` and eventually force an unclean power-off (risking filesystem corruption, especially on exFAT/NTFS).
  4. **Combined hook hard-kill window exceeds default `shutdownTimeout`:**
     `stopping_docker` (`45 + 15 = 60` s) plus `unmounting_disks` (`22 + 15 = 37` s) totals 97 s before counting Unraid's own Docker stop, VM shutdown, SMB stop, and disk unmounts.
- **How likely:** Low-Medium on typical single-volume setups; Medium on servers with multiple busy volumes, long dependent delays, or active idle-lock/cron usage.
- **How bad:** High — volumes left mounted during a forced power-off risk data corruption and an unclean shutdown.
- **Suggested fix:**
  1. Remove the one-shot `cancelled=no` guard in `stopping_docker` and `unmounting_disks` (call `cancel-unlock` on every code 6 iteration; it is a fast no-op when no unlock is active).
  2. In `do_dismount()`, only run the 2-second `umount` retry loop when a share was actually closed while Samba was running (`$closed_share`), not unconditionally.
  3. In `command_idle_check()` and `start_dependents()` / `command_start_dependents()`, check `array_started()` before each volume/dependent and break `sleep($delay)` into 1-second slices that abort if `!array_started()` or `$GLOBALS['vcm_stop']`.
  4. In `dismount_all()`, divide the remaining time budget fairly across remaining volumes (or send `SIGTERM` to all busy volumes' holders together when time is tight) so one stubborn volume cannot starve the rest.

## S2. Medium: `.plg` release state is out of sync with `HEAD`, updates ignore mounted volumes (`LIFE-6`), and removal partially tears down state before aborting

- **Confidence:** Confirmed by reading `plugin/veracrypt.mount.plg`, `.github/workflows/release.yml`, and verifying the package SHA-256 in memory.
- **Where:**
  - `plugin/veracrypt.mount.plg` (lines 5–6, 20–28, 39–42, 101–135)
  - `.github/workflows/release.yml` (lines 36–56)
  - Commit `b69c8f6` vs `d6fef06`.
- **What could go wrong:**
  1. **`.plg` SHA-256 does not match current `HEAD` (pre-release blocker):**
     `plugin/veracrypt.mount.plg` pins version `2026.11.27q` and SHA-256 `8160848e4d45f1a39283ecaa1542255cb032eccd390da0781e12e2e3f375f28f`, which matches commit `d6fef06` byte-for-byte. Commit `b69c8f6` (`HEAD`) modified `scripts/vcmount` (producing SHA-256 `357e3bc7...`) without rebuilding the `.plg`. Tagging `HEAD` without running `scripts/build.py <version>` will fail `.github/workflows/release.yml`'s `--check` gate, and users installing from `main` today will not get the `b69c8f6` TrueCrypt fix.
  2. **Plugin update ignores mounted volumes and running actions (`SPEC.md` `LIFE-6` gap):**
     `upgradepkg --install-new --reinstall` (line 39) replaces `scripts/vcmount`, `include/*.php`, `event/*`, and `js/*.js` immediately while volumes are mounted or while an unlock, dismount, or cron check is running. If a future update changes IPC flags, JSON fields, or runtime marker formats, an in-flight action or open WebUI tab can fail mid-operation.
  3. **Plugin removal partially dismounts and stops containers before aborting:**
     Lines 106–117 run `vcmount dismount --all`. If Volume 1 is idle and Volume 2 is busy, Volume 1 is **dismounted and locked**, and Volume 2's **SMB share is removed and its dependent containers are stopped (or killed)** before `dismount --all` exits with code 5 and removal prints *"Not removed: a volume is still mounted and in use"* and aborts. This contradicts `SPEC.md` `LIFE-6` (*"does not dismount automatically"*) and surprises users who read `README.md` (*"if one is still in use, the removal stops and nothing is taken away"*).
  4. **Non-busy errors trap users from uninstalling a broken plugin:**
     Line 114 checks `elif [ "$code" -ne 0 ]` and prints *"Not removed: a volume is still mounted and in use"* even if `vcmount` exited with code 1 (e.g., PHP error or broken `/var/run/vcmount`) while **zero** volumes are mounted — blocking plugin removal through the WebUI.
  5. **Narrow cron race and leftover Samba hook entries on removal:**
     Cron is removed at lines 119–120 *after* `dismount --all` (line 106); if the minute boundary fires between lines 106 and 120, `vcmount check` can run alongside `removepkg` or recreate `/var/run/vcmount` after line 125. Also, `rmdir /etc/samba/veracrypt-shares` (line 122) silently leaves behind any orphaned `.conf` files and their `include =` lines in `/etc/samba/smb-unassigned.conf` if an unmounted volume had a leftover share.
  6. **CI checks miss shell, JS, and XML validation:**
     `.github/workflows/release.yml` runs `php -l` on PHP/page files and `build.py --check`, but does not run `bash -n` on `event/*` or `usr/local/sbin/vcmount`, syntax-check `js/*.js`, or validate `plugin/veracrypt.mount.plg` XML well-formedness.
- **How likely:** Certain for (1) until rebuilt; Low-Medium for (2)–(5) once strangers update/uninstall via Community Applications.
- **How bad:** Medium — unexpected container kills on aborted uninstall, broken uninstall path on unexpected exit code, or mid-action file replacement on update.
- **Suggested fix:**
  1. Run `python scripts/build.py <version>` and commit `.plg` before tagging/submitting to CA.
  2. Decide whether removal/update should refuse whenever `/dev/mapper/vcm-*` exists (matching `SPEC.md` `LIFE-6`, zero side effects) **or** keep auto-dismount on removal and update `SPEC.md` and `README.md` to warn that earlier volumes/shares/dependents may be stopped even if a busy volume aborts removal.
  3. On removal, only abort when `code` is 5 or 6 (or when `/dev/mapper/vcm-*` actually still exists), so a code-1 error with nothing mounted cannot block uninstall. Disable cron *before* `removepkg`, or wait briefly / clean `/var/run/vcmount` after `update_cron` + `removepkg`. Run `vcmount repair-shares` before `removepkg` (or clean stale `veracrypt-shares` include lines in `smb-unassigned.conf`).
  4. Add `bash -n` on `src/.../event/*` and `src/usr/local/sbin/vcmount`, `node --check` on `js/*.js`, and Python XML parsing of `plugin/veracrypt.mount.plg` to `.github/workflows/release.yml`.

## S3. Medium: Forced dismount can kill processes inside containers directly, stop unrelated containers (`MNT-2`), and drop unrelated SMB sessions

- **Confidence:** Confirmed by reading `scripts/vcmount` (`holders()`, `mount_users()`, `end_programs()`, `do_dismount()`). Exact container mount propagation under `MNT-2` **needs verification on the server**.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `holders()` (lines 1961–1995), `mount_users()` (lines 2019–2055), `end_programs()` (lines 2093–2144), `do_dismount()` (lines 2183–2254).
- **What could go wrong:**
  1. **`holders()` does not exclude container processes (unlike `idle_blockers()`):**
     When a Docker container bind-mounts a volume at the same path as the host (for example `/mnt/addons/vault:/mnt/addons/vault` or `/mnt/user:/mnt/user` under `MNT-2`), `/proc/<pid>/fd/*` and `/proc/<pid>/maps` match `$point`. During `dismount --force`, `end_programs()` sends `SIGTERM` and `SIGKILL` directly to the processes inside the container, bypassing `docker stop` (and if the container has a restart policy, Docker immediately restarts it, causing the dismount to fail or race).
  2. **Stopping unrelated containers under `MNT-2`:**
     When a volume is mounted inside an Unraid user share (`/mnt/user/<share>/<folder>`), any unrelated container with a `Slave`/`Shared` bind mount of `/mnt/user` receives that mount in its mount namespace. During manual `dismount --force`, `mount_users()` matches the volume's device number in `/proc/*/mountinfo` and runs `docker stop -t 10` on those unrelated containers (such as databases or media servers), even though they were never listed as dependents.
  3. **Killing `smbd` workers on `MNT-2` parent shares:**
     `remove_share()` only closes the plugin's own share (`$name`), never the parent Unraid share of an `MNT-2` volume. If a Windows client has a file open in the volume through the parent share, `holders()` finds `smbd` and `end_programs()` kills the `smbd` worker — abruptly disconnecting **all** other Unraid shares that client has open.
- **How likely:** Medium for users who use `MNT-2` (mounting inside a share) or 1:1 container bind mounts and trigger a forced dismount.
- **How bad:** Medium — unexpected kill of unrelated containers or dropped SMB sessions on other shares.
- **Suggested fix:**
  1. In `holders()` (or `end_programs()`), skip processes where `process_container_id("/proc/$pid") !== null` and handle containers uniformly via `docker stop` (and in `do_dismount()`, if `umount` fails because a 1:1 container holds `$point`, stop those containers via `docker stop` cleanly rather than raw `kill`).
  2. In the "Force dismount" confirmation popup (`js/vcmount.js` line 1266), warn explicitly when `mount_at` is under `/mnt/user/` that unrelated containers sharing `/mnt/user` and active SMB connections to that share may also be stopped/disconnected.

## S4. Medium-Low: Privacy violation (`PRIV-2`) — an array-stop timeout logs unsaved ("Mount a file once") volumes to syslog

- **Confidence:** Confirmed by reading the code.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `dismount_all()` (line 2295).
- **What could go wrong:**
  ```php
  log_event("dismount of \"$name\" was not started: no time was left", isset($config[$name]));
  ```
  The second argument of `log_event(string $message, bool $notify = false, ...)` controls only whether an **Unraid notification** is sent — **not** whether a line is written to `/var/log/syslog`. Everywhere else in `scripts/vcmount`, unsaved volumes are protected with `if ($saved) { log_event(...); }`. Here, if an array stop runs out of time (`out_of_time(5)`) while an unsaved ("Mount a file once") volume is mounted, `log_event()` writes straight to syslog (which Unraid copies to the flash drive at shutdown and includes in diagnostics). When `"Show volume names in logs"` is enabled, the unsaved volume's name itself is written to syslog — directly breaking `PRIV-2` and `README.md`'s promise (*"leaves no trace in the plugin's settings or log"*).
- **How likely:** Low (requires an unsaved volume to still be mounted when `unmounting_disks` runs out of time).
- **How bad:** Low-Medium — leaks the existence (and, if `log_names` is on, the name) of an unsaved volume to persistent syslog/diagnostics.
- **Suggested fix:** Guard line 2295 with `if (isset($config[$name])) { log_event("dismount of \"$name\" was not started: no time was left", true); }`.

## S5. Medium-Low: Remaining `root` path, permission-tool, and SMB user validation edges

- **Confidence:** Confirmed by reading the code. Unraid's `/usr/local/sbin/newperms` handling of spaces/symlinks **needs verification on the server**.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/scripts/vcmount`: `valid_mount_at()` (lines 1431–1437), `check_mount_point()` (lines 1440–1473), `do_mount()` (lines 1652, 1672–1679), `command_fix_permissions()` (lines 3452–3469), `user_exists()` (lines 1144–1153).
- **What could go wrong:**
  1. **Mounting into a misspelled `/mnt/user/<share>/<folder>` creates a brand-new Unraid user share as `root`:**
     `valid_mount_at()` allows any `/mnt/user/<x>/<y>`, and `do_mount()` runs `mkdir($point, 0755, true)` without checking that `/mnt/user/<x>` already exists. On Unraid, creating a top-level folder under `/mnt/user/` automatically creates a new Unraid User Share on an array/pool disk. A typo in the share name silently creates an unwanted share.
  2. **Trailing spaces in `mount_at` break Samba path alignment:**
     `valid_mount_at()` does not reject leading/trailing whitespace in path components. While the WebUI trims `#e-mount-at`, a CLI/API `save-config` with trailing spaces in `mount_at` writes `path = /mnt/user/share/dir   ` to Samba, which strips trailing whitespace and serves the wrong directory.
  3. **`command_fix_permissions()` releases the engine lock immediately while `newperms` runs in the background:**
     Line 3457 takes `$lock = take_lock()`, spawns `/usr/local/sbin/newperms "$point"` in the background (`&`), and returns immediately (releasing the lock). Nothing prevents launching multiple overlapping `newperms` runs on the same volume, and a subsequent dismount can race with a starting `newperms` process. Also, whether Unraid's `/usr/local/sbin/newperms` safely handles spaces/special characters in `$1` and never follows symlinks inside the volume out into the host filesystem has not been verified on the server.
  4. **`user_exists()` still accepts Linux system accounts (`UID < 1000`):**
     Unlike `command_options()` (line 2552, which filters `$uid >= 1000 && $uid < 60000`), `user_exists()` (lines 1144–1153) accepts any entry in `/etc/passwd` — including `root`, `nobody`, `daemon`, `sshd` — if supplied via `save-config` or hand-edited `volumes.json`. (Unraid's Samba password database normally only has real Unraid users, so this is defense-in-depth.)
  5. **No `clearstatcache(true)` before the post-unlock `check_mount_point($point)` re-check:**
     `do_mount()` calls `check_mount_point($point)` before `cryptsetup` (line 1522) and again up to 3 minutes later (line 1652). PHP caches `realpath` entries for 120 seconds by default (`realpath_cache_ttl`). Calling `clearstatcache(true)` at the start of `check_mount_point()` ensures PHP never serves cached metadata across a slow unlock.
- **How likely:** Low (requires typo in `MNT-2`, concurrent clicks on `fix-permissions`, or crafted `save-config`).
- **How bad:** Low-Medium — accidental Unraid share creation, overlapping `newperms` runs, or defense-in-depth weakening.
- **Suggested fix:**
  1. For `/mnt/user/<share>/...`, verify `is_dir("/mnt/user/$share") && !is_link("/mnt/user/$share")` in `check_mount_point()` before creating subfolders, and reject trailing spaces in `valid_mount_at()`.
  2. Call `clearstatcache(true)` at the start of `check_mount_point()`.
  3. Filter `$uid >= 1000 && $uid < 60000` in `user_exists()` to match `command_options()`.

## S6. Low (Defense-in-Depth): Secret memory-clearing fix (`AUDIT-2026-11-27b` S3) does not actually free the password or PIM during unlock

- **Confidence:** Confirmed by reading `include/action.php` and `include/actions.php`.
- **Where:**
  - `src/usr/local/emhttp/plugins/veracrypt.mount/include/action.php` (lines 40–51)
  - `src/usr/local/emhttp/plugins/veracrypt.mount/include/actions.php` (lines 76, 207–208, 260–261, 358).
- **What could go wrong:**
  Following `AUDIT-2026-11-27b` S3, line 358 of `actions.php` was added:
  ```php
  // Drop the secret from PHP memory as soon as the pipe has it (audit 2026-11-27b S3).
  $stdin = null;
  ```
  However, in PHP strings and arrays are reference-counted (copy-on-write):
  1. `vcm_handle()` passes `$stdin` **by value** to `vcm_run()` (line 260), and does not `unset($stdin)` until line 261 — *after* `vcm_run()` returns (up to 180–300 seconds later). Setting `$stdin = null` inside `vcm_run()` only drops `vcm_run()`'s reference, leaving the joined `"password\npim\n"` buffer live in `vcm_handle()`'s stack frame.
  2. Even before that, `$post['password']` and `$post['pim']` remain live inside `$post` in **both** `action.php` (lines 40–51) and `vcm_handle()` (line 76) for the entire duration of `vcm_run()`.
  As a result, the plaintext password and PIM stay in PHP-FPM process memory for the full unlock duration (up to 3 minutes), rather than being released as soon as the pipe accepts them. (Only `root` can read PHP-FPM memory, and PHP cannot guarantee zeroing freed heap pages anyway, so this is purely defense-in-depth.)
- **How likely:** Certain on every web mount.
- **How bad:** Low — requires `root` memory inspection during an active unlock; no disk, log, or network exposure.
- **Suggested fix:** Pass `$post` by reference from `action.php` (or unset `$post['password']` and `$post['pim']` immediately after extracting them in `vcm_handle()`, and clear `$post` in `action.php` before calling `vcm_handle()`), and pass `$stdin` by reference to `vcm_run()` (with `#[\SensitiveParameter] ?string &$stdin`) so `$stdin = null;` on line 358 actually drops the last PHP reference immediately after the pipe write completes.

## B1. Medium-High (Confirmed): Clicking "Skip" during "Mount all" while unlocking is in progress corrupts the mount dialog and queue
